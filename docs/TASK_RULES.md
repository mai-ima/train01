# タスクのルール(割り込み指示・タスク追加・順番)— 2026-10-12 集約版

`CLAUDE.md` に散在していたルールを1枚にまとめたもの(元の記述は削除していない)。**常時有効**。

## 1. 命名(net/taxonomy.md)
- 件名は **【群記号+番号】**(例: 【E6】【C14】)。番号は同じ群内で重複させない(tasks.json で最大番号を確認)。
- **【S-】接頭はユーザーが「最優先」と明記した時だけ**。「優先」「大事」などは S- を付けず、`docs/TASK_ORDER.md` で順番を上げる。
- Z群は Z-A/B/C/D/F/G に細分。CO=コンテキスト関係、X=監査、R=路線図、…(taxonomy.md 参照)。

## 2. ユーザーの割り込み指示を受けたとき(毎回・この順)
1. **作業は止めない**(撮影は背景のまま。待ちは Monitor+小作業。sleep での待機はしない)。
2. 指示を **即記録**: `CLAUDE.md` 末尾(日時つき・既存の記述は消さない)/`net/session_state.md`/`migration/tasks.json`。
3. 指示から **タスクを作る**: 指示の言葉どおりのタスク+それに必要な関連タスク。`TaskCreate`(TaskList)と tasks.json の両方に。
4. **再最適化**: 再細分化・具体化・順番変更・重複整理 → `docs/TASK_ORDER.md` を更新。
5. 作業を再開し、結果は日本語で簡潔に報告(未検証・未達は正直に)。
6. 節目で `net/mktasklist.py` を実行して `docs/TASK_LIST.md` を再生成し、コミット+push(コミット文は日本語+トレーラー2行)。

## 3. ユーザーが「タスクを追加して」と頼んだとき
- 頼まれた内容を **そのまま** タスク化(件名はユーザーの言葉を生かし、群記号をつける)。
- 「全て/必要なもの全て」と言われたら、**今の状況で必要と判断するものも含めて**追加(理由を description に書く)。以前のセッションのタスクを含める指示なら tasks.json の未完了を全て TaskList へ。
- 追加後に ID を報告し、実行順(フェーズ)も示す。完了済みは TASK_LIST.md に記録(TaskList へは入れない)。

## 4. 自分でタスクを追加してよい場合(ユーザー補足 2026-10-12)
- 作業中に見つけた不具合・所見・必要な作業は、**ユーザーの指示を待たず随時追加**する(例: 撮影で見つけた E4/B8/B9)。
- 追加したらその場で TaskList・tasks.json・TASK_ORDER を更新する。

## 5. 状態の更新
- 着手=in_progress、完了=completed。完了時は migration/task_reports.json に報告(1〜3文)を追記。
- 進行中が増えすぎたら小分けにして実行順の先頭へ。

## 6. 優先度の読み方
- 「最優先」→ S- 付きで即着手(他の作業は区切りまで進めて中断)。
- 「優先」→ S- は付けず、現在の作業の次に着手(フェーズ内の先頭へ)。
- 通常の指示 → 作業を止めずに追加し、フェーズ順に消化。

## 7. レンダの運用(W6 計測結果・2026-10-16 採用。旧「2本まで」を置き換え)
計測条件: 4コア/15GB、`--draft` 960px 24spl、1駅=3視点×人物あり/なし(6枚)、`RENDER_THREADS` 固定。
| 同時本数 N × スレッド | 全体所要 | スループット |
|---|---|---|
| 1 × 4 | 206 s | **17.5 駅/時** |
| 2 × 2 | 472 s | 15.3 駅/時 |
| 3 × 1 | 705 s | 15.3 駅/時 |
| 4 × 1 | (計測中。結果は下に追記) | |
結論(暫定・N=4 確認後に確定): **レンダ(Cycles)は同時1本・4スレッドが最速**。本数を増やしても CPU が飽和済みで、むしろ遅くなる。
- 運用: レンダ/バッチは同時1本(`RENDER_THREADS` は未指定=4)。複数本を並べない。
- 並行してよいもの: コード編集・調査・記録・`--no-render` の検査(modelcheck/interf/trackcheck 等。レンダ中は計測ノイズになるので重いものは避ける)。
- 旧規則(「2本まで」「レンダ1本(2コア)」)は無効。以後これに従う。
